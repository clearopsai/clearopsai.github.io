Issuer authorisation path Sample · fictional client

Prepared for Northwind Pay (invented) · Confidential in a real engagement

Summary

The issuer authorisation path has one known evidence gap and one that was not known.

The known gap is the absence of an independent record on the return path, already tracked internally. The gap that matters more is in the response log itself. The response log records a decline when the issuer declines, and also when the gateway times out waiting and synthesises one. Both are written in the same format. Nothing in the record distinguishes them.

A decline in that log therefore does not establish that the issuer answered. This is the mechanism that made the 14 March investigation take six hours, and it is not addressed by the return-path logging change currently in the backlog.

1. What was reviewed

One workflow: the issuer authorisation path between the Northwind gateway and the partner, from inbound merchant request through to the response returned to the merchant.

Method. One working session with the engineer who owns the integration, conducted by screen share, followed by review of the architecture diagram and alert definitions provided afterwards. No production credentials were used and no transaction payload contents were reviewed.

The question this review answers is narrow: at each point where the transaction changes hands, what record exists that establishes it continued past that point?

2. The path

Five handoffs, with the ownership boundary between Northwind and the partner falling at handoffs three and four.

  1. Merchant submits an authorisation request to the Northwind gateway.
  2. Gateway passes the request to the internal authorisation service.
  3. Authorisation service sends the request to the issuer. Ownership boundary.
  4. Issuer returns a response to the gateway. Ownership boundary.
  5. Gateway returns a result to the merchant.

3. Evidence matrix

Status is one of three values. Proven means a record exists that establishes the transaction continued past that handoff. Partial means a record exists but does not establish it unambiguously. Absent means no such record exists.

4. The finding

A decline does not establish that the issuer answered

When the gateway receives a response it cannot parse, or times out waiting for one, it synthesises a decline and writes it to the response log in the same format used for a decline returned by the issuer. The log records the outcome. It does not record which of the two produced it.

The consequence is that the response log reports a completed transaction with a negative outcome in both cases. A transaction for which no response was ever received is indistinguishable, in the record, from one the issuer explicitly declined.

This is what made the March investigation take six hours

Four of the six hours were spent establishing that the responses had in fact arrived. That question was only settled by obtaining the partner's own logs. The working assumption at the start of the investigation was that the partner had not sent the responses, because the Northwind record showed declines, and declines indicate the issuer answered.

Nothing appeared missing. The absence was recorded as an outcome.

The change already planned does not address it

Return-path logging, currently in the backlog, would create a record at handoff four and close the Absent row above. That is worthwhile and should proceed. It does not change the behaviour at handoff five: the gateway will continue to synthesise declines that are indistinguishable from issuer declines in the response log.

5. What this establishes, and what it does not

Establishes. The response log cannot distinguish an issuer decline from a synthesised decline. Any figure derived from that log which counts declines includes an unknown number of transactions for which no response was received. The same evidence structure is present on a second issuer integration reviewed during the session, so this is a property of the gateway rather than of one partner relationship.

Does not establish. How frequently this occurs; determining that requires correlating response-log declines against the outbound request record over a period, which was outside the evidence available in this review. Whether any specific historical transaction was affected. The correctness of message or payload contents, which was out of scope.

6. Evidence gaps, in priority order

  1. Synthesised declines are written to the response log in the same format as issuer declines, with no field recording which occurred. Highest priority: this gap produces a record that reads as a definite outcome, so it is not visible as a gap and will not be found by looking for missing data.
  2. No independent record is written when a response is received at the gateway, before parsing. Already tracked internally. Closing this makes gap one detectable but does not resolve it on its own.
  3. The same structure exists on at least one other issuer integration. Any remediation applied to one path should be applied at the gateway rather than per integration.

7. A check that can be run without ClearOps

The check is a count of response-log declines that have no corresponding issuer response event recorded against the same correlation ID.

Run today, that query returns every decline in the log, because no issuer response event exists to correlate against. That result is itself the confirmation of gap two. Once a receipt event is written at handoff four, the same query returns only those declines for which no response arrived, which is the number that cannot currently be produced.

Suggested shape: declines in response log, over a period, where no issuer_response_received event exists for the same correlation ID

Running it monthly, and expecting zero, converts an invisible condition into a number that is either zero or is not.

8. What would have shortened the investigation

From the session, in the engineer's own assessment: if the return path had been independently visible on 14 March, roughly four of the six hours would not have been spent, because the question of whether the responses arrived would have been answerable from the Northwind record alone rather than by requesting the partner's logs. The remaining two hours were spent on the configuration push itself, which was correctly identified once the responses were confirmed received.

The limits, as they appear in a real report. This review establishes what the available evidence does and does not prove about one workflow. It is not an audit, a security assessment, or a determination of legal responsibility between the client and any third party. Findings are limited to the evidence made available during the engagement. Recommendations are advisory; evaluation, implementation and testing of any change remain with the client.
