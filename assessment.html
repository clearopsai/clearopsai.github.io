A worked example
Why this is here. The honest answer to "who else have you done this for" is that ClearOps has no clients yet. So instead of a case study I cannot produce, here is the same assessment run at full depth on my own estate, published whole, including the parts that make me look bad. Judge the work rather than the reference list.

What a two-server estate was hiding

An infrastructure assessment, run on my own systems. 28 July 2026.

I run two Linux servers: a workstation at home that does heavy processing, and a cloud box that hosts the public-facing services. Both are mine. I built them, I maintain them, and I look at them most days.

Yesterday one of them ran out of disk in the middle of a task. That's a boring failure with a boring fix, so I did what I'd do for a client instead: I stopped, and I audited the whole estate properly.

I found eleven problems. Two were security exposures serious enough to fix that night. One had been silently failing 1,778 times. None of them were alerting anybody.

This is what turned up, and why I think the pattern matters more than any individual finding.

The disk wasn't full

That was the presenting symptom, and it was wrong.

The root volume was at 100% with writes failing. But the machine had 311GB free. It was sitting on three separate logical volumes: root was suffocating at 100%, while a second volume had 221GB free and a third had 90GB free. There was also a 4.6TB network storage box, already configured and working, holding almost nothing.

Nobody had noticed because the obvious command lies. du on the root filesystem doesn't cross mount boundaries, so it reports the root volume's contents and silently omits the other two. If you're used to trusting that number, you conclude you need to buy more disk.

The finding wasn't "you're out of space." It was "you already own 311GB you aren't using, and here's why it's stranded."

Cause of the pressure: a 46GB backup mirror living on the volume with no room, backing up data that mostly lived on the volume with 221GB free. Moving it wasn't the fix either. A timer regenerates that directory hourly, so deleting it just means it returns before lunch. The fix was one variable on line 6 of the script.

The backup had never backed up the file it was told to

While I was in that script, I checked whether it did what it claimed.

A specific file was listed as a backup source. The script appends a trailing slash to every source path, which is correct for directories and invalid for files. So every run produced a path like notes.md/ and rsync answered, accurately, "Not a directory."

The error was caught by a handler that prints a warning and continues. The job carried on, reported success in the ways anyone would check, and never once copied that file.

I counted the log entries. 1,778. Once an hour, for about two and a half months. Every line said exactly what was wrong.

Two more problems in the same script:

A database was being stored three times. The SQLite hot-backup stage walked into the backup directory itself and captured copies of copies. One 5GB database occupied roughly 15GB. That alone explained a third of the pressure on the volume that was full.

The job exited non-zero on every run. A sort | head pipeline under set -o pipefail: head closes the pipe after ten lines, sort dies on the broken pipe, set -e terminates the script there, and the final stage that writes the success timestamp never executes. The backup completed. The reporting didn't. Anyone watching exit codes would have concluded, wrongly, that backups were failing, and would eventually have stopped watching.

Two live security exposures

An unauthenticated public API. A containerised media-downloader service was bound to all interfaces, reachable from the open internet, three days up, with no authentication. Nothing in my current work used it. Anyone who found it could run traffic through my server and my bandwidth.

There was no firewall on the cloud box at all: ufw inactive, iptables default policy ACCEPT. That's why the above was reachable, along with several other services that had no business being exposed. The workstation was never the problem here; it has run a default-deny host firewall throughout.

And the worst one: a web portal with no authentication and 43 writable endpoints. I had assumed it was obscure enough not to matter. Obscurity isn't a control. Anyone with the URL could change application state, and several of those endpoints did more than write a record. One spawned a subprocess. One consumed a paid third-party API quota. Four launched video encoding jobs with multi-minute timeouts, which is a denial-of-service primitive handed to the internet for free.

The fix was a token gate. The part that took actual thought was the exception list: client-facing share links had to keep working without a login, because that's the entire point of them. Locking everything would have been faster and would have broken the one function that faces customers.

Work that was ordered stopped, and didn't

I'd paused a whole product line five days earlier and written a manifest recording exactly what to stop.

It stopped on neither machine. The cloud box still ran six services and fourteen scheduled jobs: transcription, encoding, caption generation, media prefetching. On the workstation, one downloader named explicitly in my own manifest was still running, and had accumulated 101 CPU-hours. It was still downloading, into a 215GB tree that nothing reads, for a product with no users.

The workstation was running 234 scheduled jobs, of which 169 belonged to the paused product. Thirty-one were duplicate twins running the same work twice.

Four failures nobody could see

A service was disabled while running. It would survive until the next reboot and then quietly not come back, taking a public endpoint with it. Everything looks healthy right up until an unrelated restart.

A protective job was failing 1,427 times a day. Its purpose was to cut network access if a privacy tunnel dropped. It hadn't executed successfully in a long time, so the protection simply wasn't there. It had written about 500MB of journal saying so.

Another job failed every four minutes and never appeared in the failed-units list, because its own timer restarted it before anyone looked. A unit that fails and is immediately reset is invisible to every check that asks "what's failing right now."

A VPN was logged out, so three monitoring services were bound to an IP address that no longer exists. Monitoring was, in the most literal sense, not.

What I did

Firewall on the cloud box, allowing only SSH and the private network. Container stopped. Token authentication on the portal, with client share links deliberately left public. The paused fleet actually stopped on both machines: twenty units on one, 166 on the other, taking scheduled jobs from 234 to 68 and failed units from 22 to zero. The disabled-but-running service enabled so it survives a reboot. Three backup script bugs fixed.

Two numbers moved: the cloud box's load average went from 1.46 to 0.16. The workstation's root volume went from 4GB free to 80GB, without deleting anything that wasn't either regenerable or verified on the storage box first.

Every change was written to a reversal script before it was made. Every deletion was verified before it happened: the backup was checked with an integrity check and a row count against the live database, and the archived directory was streamed back and its file count compared against the original, 23,353 against 23,353, before a single local byte was removed.

One remote-firewall habit worth stealing: arm the rollback before you enable the rule. A timer set to disable the firewall in ten minutes, cancelled only after a fresh connection proves the rule didn't lock you out.

The pattern

Not one of these was hard. There's no clever diagnosis here, no exotic failure. Every single one announced itself in a log, a status field, or an exit code.

The problem was never that these systems were broken. It's that they were broken quietly.

Loud failures get fixed, because someone is standing there. Quiet failures accumulate: the backup that reports success, the alert that fires so often it's furniture, the job that fails and restarts before anyone looks, the service that runs today and won't survive a reboot in March. They cost nothing until the day they cost everything, and by then the log that would have explained it is 1,778 entries deep.

I do this work. If you have infrastructure and nobody whose actual job is to go looking, I'd guess your estate has its own version of these. It takes about two weeks to find them and the report is yours either way.

The uncomfortable part, for me, is that this is my own estate. I look at it most days. It still took a deliberate audit to see any of it, because none of it was on fire.

That's exactly the point.

Six days later

A follow-up to "What a two-server estate was hiding." 4 August 2026.

Last week I audited my own infrastructure and published what I found. Eleven problems, none of them hard, all of them quiet. The argument was that quiet failures accumulate while loud ones get fixed, because nobody is standing there when a log line is the only thing complaining.

Six days later I ran the same audit again.

I expected to write a short note saying it held. Instead I found that one of my own numbers was false when I published it, and I watched the estate erase a failure while I was looking at it.

The number I got wrong

I wrote that the cleanup took the workstation from 234 scheduled jobs to 68, and failed units from 22 to zero.

It did not.

There are 165 active scheduled jobs on that machine tonight. And the reason is more embarrassing than drift, because they did not creep back. 98 of the jobs I reported stopping have been running continuously since the minute I stopped them.

They show a state I should have recognised, because it is the same shape as everything else in the original piece:

`` UnitFileState=disabled ActiveState=active ``

Disabled means it will not start after a reboot. Active means it is running right now. I disabled them, confirmed they were disabled, and wrote down the number that command gave me. The command was answering a different question than the one I thought I was asking.

I checked what the system said about itself instead of checking what the system was doing. That is the exact error the article was about, made by the person writing the article, in the paragraph reporting the fix.

Failed units are not zero either. I sampled four times across one night: 14, 14, 15, 14.

Then it happened in front of me

At 00:30:19 a unit failed. At 00:31:25 it appeared in the failed list, where I saw it. At 00:34:51 it was gone from that list, and it had not run again in between.

Something on the box clears failure state on a schedule. So a unit can fail every few minutes forever and never appear in the one check most people run, which is systemctl --state=failed. There are two of these on my workstation right now. Together they generate more than six times the failure volume of the killswitch I led with last week.

Last week I described this failure mode in the abstract, as one of four things nobody could see. This week I have the timestamps.

The fix that removed the alarm and not the risk

Last week I found a protective job failing 1,427 times a day. Its purpose was to cut network access if a privacy tunnel dropped.

I stopped the noise. I did not restore the protection. Six days on, the protection is still absent, and the containers it existed to protect are still running.

That is worse than the original state, and it is worse in a specific way: before, something was screaming into a log every minute. Now it is quiet. If I had walked away after publishing, the only signal that this was broken is the one I personally switched off.

What actually held

Not everything drifted, and the split is the interesting part.

The security fixes held completely. The portal token gate still rejects every dangerous endpoint from the public internet, six days on, including the one that could have launched video encoding jobs on demand and the one that burned a paid API quota. The exception list for client share links has not grown by a single entry. The container is still stopped. It has not restarted once.

One backup fix held and I can prove it. The file that had never once been copied, in 1,778 attempts, is now in the backup with the same size, the same checksum and the same modification time as the live file. It is not merely fixed in the code. It is doing work every hour.

The hygiene fixes did not hold. Timers, failed units, disk hygiene, and the protection I silenced.

Then I noticed the split runs along a cleaner line than security versus hygiene.

Every single regression is on one machine. The cloud box held on every axis I could test: firewall still up, still nothing but SSH reachable from the internet, zero failed units, and not one of the paused product's jobs running. The workstation is where all of it came back.

The difference is not that I was more careful with one box. It is that the workstation runs a system that regenerates itself, and the cloud box does not. The paused jobs there are configured to restart. Disabling them was an instruction the machine was free to disregard, and did.

A fix that has to win an argument with a running system every hour is not a fix. It is a preference.

The original failure, recurring on schedule

The piece opened with a root volume at 100% while 311GB sat unused on other volumes.

Tonight root has 51GB free. Six days ago I left it with 80. That is about 29GB in six days, and at that rate it is full again around the middle of the month.

Meanwhile there is 208GB free on the other two volumes on the same machine. The identical stranding, in the identical place, five weeks after I wrote it up.

With one difference that makes it worse. Last time I could have grown the volume, because the group had room. It does not now. It is fully allocated. So the escape hatch I used the first time is closed, and the deadline is real rather than notional.

I have known about the 191GB directory this is competing with since I wrote the first piece. It is still there. I have not decided what to do with it, and not deciding is itself the thing filling the disk.

While I was writing this

The console I use to run this business raised the highest-priority alert it has: a reply from a prospect. Then it raised it again. It raised the same two alerts 130 times in sixteen hours.

Neither was a reply. Both were out-of-office autoresponders. The watcher treated any message from a tracked address as an answer, and it re-raised the alert on every run instead of only when something changed.

So the system I built to stop quiet failures spent a night burying my actual task list under 130 copies of a false alarm, and marking two people as having answered me when they were on holiday. That second part is the expensive half: marking them answered took them out of the follow-up queue, so the two people who wrote to me with the exact date they would be back were the two I would never have chased.

The part I like least is that I was warned. Two days earlier, the review I run over my own console reported that four of the thirteen items on my list were the system filing tickets about itself, and it spelled out where that ends: "dedup is per head, so all nine departments can each hold one open ticket at once. That would be nine invented items against eight real ones."

I read that, agreed with it, and fixed it by hiding tickets of that one type from that one list. The warning was about a mechanism that invents work. My fix was about a category name. Two days later the same mechanism came back through a door the fix did not cover, and the score was not nine invented against eight real. It was a hundred and thirty against nine.

I found it because I went looking. Nothing was on fire.

What I would tell a client

Three things, and I would have said the first two last week with more confidence than I had earned.

Check the effect, not the report. Disabled is not stopped. Active is not working. Exit zero is not success. Every wrong number in my own audit came from reading a status field instead of observing a behaviour.

A silenced alarm is a worse state than a loud one. If you turn off a check, write down what it was protecting and when you will restore it, or you have converted a visible problem into an invisible one and called it progress.

Fix the mechanism, not the symptom you can see. Twice in one week I was handed an accurate warning and closed it by making the visible instance go away. Both times the underlying thing came back somewhere the fix did not reach. If a finding names a mechanism, the fix has to name the same mechanism.

Re-run the audit. Not because the first one was careless, but because an estate that regenerates itself will undo anything that has to be re-won every hour. The value is not in the finding. It is in the second look.

I do this work. The uncomfortable version, which is the one worth publishing, is that I did it on my own systems, wrote it up carefully, got a number wrong, and only caught it because I went back six days later and checked the machine instead of my own report.

That is the argument for going back.

Correction, 7 August 2026

The first writeup says the paused fleet took scheduled jobs "from 234 to 68." I cannot stand behind that number, so here it is corrected rather than quietly edited.

Counted today: 217 scheduled jobs are active on that workstation, 169 user timers and 48 system timers. Whatever 68 measured, it was not what was running.

Two things went wrong, and both are ordinary.

The count came from systemctl reporting units as disabled. Disabled is a statement about whether a unit starts at boot. It says nothing about whether the unit is running right now, and a service with Restart=always will sit there disabled and running forever. I read a field that answered a question I had not asked.

And the fleet came back. Units that were stopped have restarted across reboots, because disabling a unit does not survive the thing that re-enables it. That is the resurgence the original writeup was written to prevent, happening to the person who wrote it, on the machine he audited, inside a week.

I am leaving both writeups up unchanged above this line. The number was wrong, it was wrong in the flattering direction, and nothing alerted me. That is the entire argument of the first piece and I am not going to make an exception for myself.

Root disk today: 87% used, 33GB free. A 55MB database has generated 48GB of write-ahead log through a replication tool that reports healthy, because the retention window is thirty days and it snapshots hourly against a file written every ten seconds. At the current rate that volume fills in about ten days. It is the same class of finding as the backup that ran 1,778 times and copied nothing: the tool is working exactly as configured, and the configuration is the defect.
